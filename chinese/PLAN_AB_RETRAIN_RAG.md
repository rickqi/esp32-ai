# 中文模型优化方案 A + B：重训 + RAG 增强

> 目标:解决 zh4-ds 模型"能生成医学文本但不能正确回答医学问题"的根本缺陷。
> 核心结论:12.5M 参数模型无法靠数据堆叠学会医学问答(2026 年研究实测 360M 模型 RAG 问答 0% 准确率),需 **A 重训提升文本质量 + B RAG 提供事实知识** 双管齐下。

---

## 1. 现状诊断

| 项目 | 现状 | 问题 |
|---|---|---|
| 模型 | zh4-ds, 12.5M 参数 | 容量不足以存储/推理医学知识 |
| 预训练语料 | D:\docs\raw OCR 文档, 70M 汉字 | 含噪音(LaTeX/表格转储), 非医学科普 |
| SFT 数据 | 1059 条指令(DeepSeek 生成 + 搜索日志) | 规模不足、多样性差 |
| 问答能力 | 实测"甲状腺切除后是否会晕倒"回答失败 | 生成模板文本 + LaTeX 噪音, 无事实回答 |

**根因**:数据质量 + 参数量双重瓶颈。A 解决数据质量,B 解决参数量限制。

---

## 2. 方案 A:重训(提升文本生成质量)

### A1. 数据源升级(替换 OCR 语料)

从魔搭/HF 下载干净医学数据,替换 `D:\docs\raw`:

| 用途 | 数据集 | 规模 | 魔搭镜像 | 下载命令 |
|---|---|---|---|---|
| **预训练**(替换 OCR) | `shibing624/medical/pretrain/` | 360K 百科 + 8.5K 教材 | `zjydiary/Medical` | `modelscope download --dataset zjydiary/Medical` |
| **SFT 主数据** | `BenTsao/本草` | 8K 指令(适合小模型) | — | GitHub `SCIR-HI/Huatuo-Llama-Med-Chinese` |
| **SFT 补充** | `HuatuoGPT2-SFT-GPT4-140K` | 142K(采样 3K) | ✅ | HF `FreedomIntelligence/...` |
| **通用指令** | Firefly 精选 | 采样 1-2K | `AI-ModelScope/firefly-train-1.1M` | ModelScope |

### A2. 数据管线改动(`chinese/prepare.py`)

```python
# 新增:从 shibing624/medical pretrain 生成训练语料
# 替换: --source D:/docs/raw → 医学百科/教材清洗文本
# 目标: 100M 字符干净中文医学文本(百科+教材为主)
```

具体:
1. 下载 `zjydiary/Medical`,取 `pretrain/train_encyclopedia.json` + `medical_book_zh.json`
2. 复用现有 `clean_markdown` 清洗逻辑(去 LaTeX/表格/噪音)
3. 与现有语料按 8:2 混合(医学百科 80% + 现有保险/法规 20%)
4. 字符级 tokenizer(vocab≈5904)可复用,无需重训 tokenizer

### A3. 训练配置(参照 zh4 已验证配置)

```powershell
uv run python chinese/train.py --d-model 160 --n-layers 8 --n-heads 8 `
  --ple-dim 192 --target-core 2500000 --steps 10000 --tag zh5
```

- 架构不变(PLE),只换数据
- 预计耗时:CPU ~20-30 分钟/万步(zh4 实测 5225s)
- 产出:`runs_chinese/ple-zh5-s42.pt`

### A4. SFT 重训(5000-10000 高质量样本)

```powershell
uv run python chinese/sft/sft_train.py --resume runs_chinese/ple-zh5-s42.pt `
  --steps 300 --eval-every 50 --instruction-ratio 0.8 --tag zh5-med
```

- SFT 数据:本草 8K + HuatuoGPT2 采样 3K + Firefly 精选 1K ≈ **12K 样本**(12× 于现 1059)
- 训练信号用已修复的 loss masking(`misaligned=0`)

### A5. A 方案预期效果

- ✅ 文本更干净(无 LaTeX 噪音,医学术语更准)
- ✅ 生成更流畅、领域风格更稳定
- ❌ **仍不能正确回答事实性问题**(容量限制)

## 3. 方案 B:RAG(提供事实知识,治本)

### B1. 架构

```
用户问题
   ↓
[ESP32 检索器] ← 医学知识库(压缩倒排索引,存 PSRAM)
   ↓ 检索到 1-2 句相关文本
[12.5M 模型] 根据 prompt 模板续写/摘取
   ↓
医学风格回答(基于检索内容)
```

### B2. 知识库构建

| 项 | 内容 |
|---|---|
| 数据源 | `Huatuo26M-Lite`(~160K 精选 QA)或 `shibing624/medical` SFT 子集 |
| 存储 | 倒排索引 + 文本块,压缩到 **1-2MB**(PSRAM 8MB 余量 ~4MB) |
| 检索 | TF-IDF 或关键词匹配(ESP32 CPU 可实时) |
| 文本块 | 1-2 句/块(小模型上下文利用差,必须短) |

### B3. 推理流程

```
1. 串口收到问题
2. 检索器从知识库匹配 1-2 句相关内容
3. 组装 prompt: [检索内容] + [用户问题] + "请据此回答"
4. 12.5M 模型生成回答
```

### B4. B 方案预期效果

- ✅ 能回答知识型问题(引用检索内容)
- ✅ 不增加模型参数、推理速度几乎不变
- ⚠️ 小模型对检索上下文利用有限——需要 RAFT 式微调(训练模型"抄写"检索内容)才能有效

## 4. 组合路线图(A+B)

| 阶段 | 内容 | 时间 | 产出 |
|---|---|---|---|
| **P0** | 下载数据(魔搭镜像,国内快) | 30-60 分钟 | 本地数据就绪 |
| **P1** | 改 prepare.py + 重训 zh5 | 1-2 小时 | `ple-zh5-s42.pt`(更干净) |
| **P2** | SFT 12K 样本重训 | 30-60 分钟 | `ple-zh5-med-s42.pt`(指令跟随改善) |
| **P3** | 构建知识库索引(Huatuo26M-Lite 子集) | 1-2 小时 | 1-2MB 检索索引 |
| **P4** | 实现 RAG 检索器 + prompt 模板(固件) | 2-3 小时 | 设备端检索问答 |
| **P5** | 端侧验证(烧录 + 实测问答) | 1 小时 | 医学问答演示 |

**总投入**:约 1 天(数据下载 + 重训 + RAG 实现)

---

## 5. 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| **12.5M 模型仍答不准** | 即使 RAG,小模型上下文利用差(研究:360M 都 0%) | RAFT 微调教模型抄检索内容;回答以"引用"为主 |
| **下载数据大** | Huatuo-26M 完整 26M 条太大 | 只用 Lite 子集(~160K)或采样 |
| **PSRAM 不足** | 知识库 + 模型 + 缓存争抢 | 知识库压缩到 1-2MB,只存高频医疗块 |
| **重训回归** | 新数据可能不如现有 OCR 语料对保险领域贴合 | 8:2 混合保留保险语料 |

---

## 6. 关键决策点

1. **先重训还是先 RAG?**
   - 若目标"文本更干净" → 先 A(P1-P2)
   - 若目标"能回答问题" → **先 B**(RAG 是唯一现实路径),A 可并行

2. **模型容量是否要增加?**
   - 保持 12.5M:RAG 是唯一答案路径
   - 扩到 30-50M:Flash/PSRAM 有余量(模型.bin 6.5MB → 15-25MB),推理速度 ~5 tok/s,QA 能力仍有限但 RAG 利用略好

3. **数据许可**
   - shibing624/medical:Apache 2.0 ✅
   - BenTsao/本草:研究用途
   - Huatuo-26M:研究用途
   - 商用需确认(本项目为个人研究,可接受)

---

## 7. 建议立即执行

**优先级:先跑 P0 + P3(数据下载 + 知识库构建),再决定 P1(重训)的投入。**

理由:
- RAG(方案 B)是解决问答的**唯一现实路径**,应最先启动
- 重训(方案 A)是"锦上添花"(改善文本质量),可与 RAG 并行
- 数据下载(魔搭镜像)是两者的共同前置依赖,先做不亏

```
P0 下载数据 → P3 知识库 → B 侧 RAG 实现 → 端侧问答
         └→ P1 重训 → P2 SFT → A 侧文本质量(并行)
```
